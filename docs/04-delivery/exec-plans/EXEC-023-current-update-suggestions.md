## User result

Show a separately labeled, point-in-time update-information suggestion for a currently authorized project manager or leader. Derive it from current project-update policy and source-authority inputs. Display the evaluated time, policy/rule revision, freshness source and state, independent completeness/authority/conflict outcomes, triggering required fact types, role-appropriate action and expected outcome. Do not present a project-created fallback as a confirmed source update; do not imply an owner is at fault, create a clarification, send a message or execute an action. Approval items and other queue categories remain unavailable. Missing configuration, inaccessible/indeterminate inputs and bounded-input failures must be distinguishable from an available observation with no suggestion. No future validity is promised.

## Authorization and transaction

One GET names one project; the server derives customer, subject and audience and reauthorizes every request. Reuse EXEC-022's exact token-role/current project-or-portfolio grant and exact PROJECT_MANAGER responsibility membership for PM; leadership needs its own current role and grant. A dual-role user gets PM wording only when the full PM predicate holds, otherwise independently qualified leadership; no supported role or inaccessible project returns private 404. No scheduled service bypass or caller-supplied subject, evidence, time, severity or status is accepted.

Extract, do not duplicate, the read-only preparation portion of project-updates.ts:553–755 so the existing write workflow and new reader share authority selection, source access, required-fact completeness, minimum trusted timestamp and freshness calculation. The shared preparation accepts the caller-owned asOf: preserve the existing write caller's clock location exactly and let the new reader choose its own post-lock clock. Preserve existing write behavior and tests. The new reader must never invoke assess/assessInTransaction/latest: the former persists assessments, audits, obligations, previews and engagement changes, while latest contains a historical result. Authority preparation can generate temporary conflict IDs; never expose them as persisted evidence. Reuse bounded prefix loading, source resolution, timestamp selection and current access checks. Required policy absent is UNCONFIGURED, not empty; prefix overflow, inconsistent input or inability to complete an authorized current read is UNAVAILABLE, never a truncated success. Preserve MISSING versus UNCONFIRMED and independent authority and conflict states. Do not infer source authority from the schedule view or publish import proposals as facts.

Use a new ReadCommitted transaction with a Project-only shared lock in its own first statement, then separate fresh statements for current grants/assignment, current policy head `FOR SHARE`, sorted required fact rows, and one DB as-of clock. Never join or preload dependent data in the potentially waiting Project-lock statement: its statement snapshot does not refresh after a lock wait. An absent policy head is UNCONFIGURED while the shared project gate is held. Fact/source/authority native guards enforce a Project lock, but the update-policy head/revision tables also permit API SQL writes without a native Project-lock trigger: supported `setPolicy` application writers follow Project → policy-head locking, and this design relies on that protocol only, not on arbitrary privileged or direct SQL writers honoring it. AccessGrant writers do not universally take Project locks: positive grant rows must be locked against update/deletion; a concurrent insert of an additional grant cannot invalidate the already locked qualifying authorization, but audience selection reflects the grants actually read and must not be described as a globally atomic grant snapshot at asOf. Confirm all supported policy, fact birth, source access, authority and version-publication mutation paths acquire an incompatible project lock before changing this observation; prove absent-row and phantom cases. Some evidence and receipt inserts have no standalone Project gate: show that they cannot affect the reader's reachable current observation until a gated fact-version or authority publication, and separately verify any connector-validation receipt dependencies. No additional source-row lock may invert writer order. If the shared project lock cannot stabilize every dependency under the supported writer protocol, do not ship this design without a reviewed lock strategy. Keep 100 required-fact and 1,000 prefix budgets and existing timeout/failure mappings. The data path must issue no business, audit, obligation, preview, engagement, stage, outbox or external writes.

## Point-in-time output and deterministic rule

Use a new update-only strict schema and pure builder, not the schedule-only DTO or generic arbitrary delivery-health signals. Input is the transaction-owned typed observation and server-derived audience; validate exact project and as-of consistency and reject arbitrary embedded signals. Return separate freshness and completeness status, source-time basis, current policy/rule revision and sorted fact summaries with accessible actual references only. Do not serialize raw prepared authority objects, restricted source IDs/values or temporary conflict IDs. A reference, if shown, must carry its real fact/version/evidence/source and access/authority revisions and be currently authorized. Preserve JSON evidence semantics without coercing it to a primitive schedule-record value; omit values rather than truncating or inventing them.

Apply availability before the advice rule: no current update policy yields UNCONFIGURED without fact details; transport, budget, snapshot or authorization-input failures yield UNAVAILABLE. Any required-fact prefix with a restricted version or access state, incomplete authority input, or REVALIDATION_REQUIRED yields the same generic UNAVAILABLE with no per-fact/source details and no suggestion. If the complete authorized input is available, existing MISSING or UNCONFIRMED outcomes (including accessible no-policy, ambiguous or conflicting authority) are available unresolved observations, preserving their distinct reasons. Only a complete and accessible input may proceed to the freshness/completeness rule below. The implementation must prove this classification from actual prepared prefix/access results; if absence cannot be distinguished from restriction without exposing hidden evidence, fail closed as UNAVAILABLE.

Proposed explicit advice priority rule update-information-v1: emit one MEDIUM-priority UPDATE_FOLLOW_UP suggestion when the existing freshness result is STALE or the existing completeness result is INCOMPLETE, based on the complete observation; use its actual source date/threshold and individual missing/unconfirmed outcomes as rationale. This priority is a review ordering rule, not a calculated project RAG or personal performance judgment. Emit no suggestion only when freshness is CURRENT and completeness COMPLETE. Unavailable or unconfigured inputs cannot produce a clear result. Keep source-authority/conflict state explicit even if a created-at fallback is used. PM wording calls for review and preparation of follow-up; leadership wording calls for reviewing the information gap and an intervention decision. No approval, `validUntil`, generic source-authority claim or arbitrary cross-category ranking is introduced.

The endpoint returns no-store. Browser state hides prior content during every revalidation, clears on session/project changes and denial, ignores late responses from an old scope, and revalidates on visibility return. It does not promise instantaneous remote revocation or retain stale fallback content.
