The health create, saved-assessment source check and schedule-policy target validation paths use locking SELECT on immutable/project-gated tables for which `pdaa_api` has no UPDATE privilege. The blocker-age helper also locks RaidItem, ProjectFactVersion, FactAuthorityConflict, AuthorityPolicyRevision and FactSourceReader this way. PostgreSQL requires UPDATE on at least one column even for FOR SHARE. Separately, operations reapplication revokes all business-table privileges but does not restore the intended `BlockerAgeThresholdPolicy` API SELECT/INSERT/UPDATE grant declared by migration 202609280002. Migration-only creator/superuser tests do not establish behavior after real grants are reapplied.

Proposed changes: remove only privilege-incompatible row-lock clauses from immutable canonical children, immutable version/conflict/policy-revision histories and FactSourceReader. Preserve Project, current-grant, canonical-parent, policy-head, ProjectFact and FactSourceAccess locking where permitted. Document that the blocker-age helper and saved-source recheck require their caller's Project SHARE gate; the existing health paths acquire it first. Under that gate, canonical birth and supported source/authority writes require Project UPDATE; sealed canonical children are immutable except the RAID reopen function, which also locks Project UPDATE before mutation. Source-reader changes and fact/authority publication take Project UPDATE. Use ordinary MVCC reads for forbidden row locks; keep original ordering, bounded limit/overflow handling and time placement. Prove all relevant writers and absence/phantom cases, including direct native paths, and don't claim protection against unsupported privileged SQL. Direct child-first maintenance DML can hold a permitted source/policy tuple while waiting for the Project trigger; a retained reader row lock can deadlock and roll back, so claim safety/fail-closed behavior, not universal deadlock freedom. Do not broaden child-table UPDATE rights. Restore exactly the migration's existing API SELECT, INSERT and UPDATE on BlockerAgeThresholdPolicy during business grant reapplication, with no DELETE, grant option or worker table access added.

Add meaningful isolated synthetic native tests that reapply the actual production business grants as the authorized schema owner, verify effective `pdaa_api` and expected ACLs, then exercise policy initialization/read, real health create on a sealed nonempty canonical graph with source-authorized blocker facts, idempotent replay/latest, nonempty target-override policy change, source-reader revocation, inaccessible evidence and a writer contention scenario. Use the existing independently created `pdaa_upgrade9_[0-9]+` fixture only after its pristine-upgrade checks, or a separately owned `pdaa_test_[0-9]+` fixture. Never change ownership or reapply privileges in the shared main test database, and never use the user's default database. Check negative identity/scope cases and no unauthorized data, and preserve current retention/audit/receipt behavior. Prove the tests fail on the pre-fix grants/query implementation, ideally separately to avoid aborted-transaction false positives. Continue requiring no new schema migration, public claim of acceptance, connector scope or external write.
